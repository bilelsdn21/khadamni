# Deploying Khadamni

The app ships as **one service**: FastAPI serves the API, the WebSocket, and the
built React frontend from the same origin. That means no CORS configuration, no
API base URL to juggle, and `wss://` works without a separate port.

```
https://khadamni.onrender.com
├── /              → React app        (built by Docker stage 1)
├── /api/*         → FastAPI routes
├── /api/chat/ws/* → WebSocket, same origin
└── /uploads/*     → redirect to Supabase Storage
```

Three free accounts are needed: **MongoDB Atlas** (database), **Supabase**
(image storage), **Render** (hosting).

---

## 1. MongoDB Atlas — the database

1. Create a free **M0** cluster at <https://cloud.mongodb.com>.
2. **Database Access** → add a user, save the password.
3. **Network Access** → Add IP Address → **Allow access from anywhere**
   (`0.0.0.0/0`). Render's outbound IPs are not fixed on the free plan.
4. **Connect** → *Drivers* → copy the connection string:

   ```
   mongodb+srv://<user>:<password>@cluster0.xxxxx.mongodb.net/?retryWrites=true&w=majority
   ```

   This is `MONGODB_URL`. Substitute the real password, and URL-encode any
   special characters in it (`@` → `%40`).

The geospatial and service-request indexes are created automatically on startup
by `connect_db()`, so there is nothing to set up by hand.

### Seeding

To load the demo providers into Atlas, run the seed script locally with
`MONGODB_URL` pointing at the cluster:

```bash
cd backend
python seed.py
```

## 2. Supabase — image storage

Uploaded avatars and portfolio images cannot live on Render's disk: the free
plan wipes the filesystem on every deploy. They go to Supabase Storage instead
(1 GB free).

1. Create a project at <https://supabase.com>.
2. **Storage** → **New bucket** → name it `uploads` → toggle **Public bucket
   ON**. Public is required so `<img>` tags load without a signed URL.
3. **Project Settings** → **API**, and copy:
   - **Project URL** → `SUPABASE_URL` (e.g. `https://abcd1234.supabase.co`)
   - **`service_role` key** → `SUPABASE_SERVICE_KEY`

The `service_role` key bypasses row-level security, so it belongs only in
Render's environment variables — never in the frontend or in git.

> Leaving `SUPABASE_URL` blank makes the app fall back to local disk, which is
> what you want for development.

## 3. Render — hosting

1. Push this repo to GitHub.
2. <https://dashboard.render.com> → **New** → **Web Service** → connect the repo.
3. Render reads `render.yaml` and picks the Docker runtime automatically.
4. Fill in the variables marked `sync: false` (Render prompts for them):

   | Variable | Value |
   |---|---|
   | `MONGODB_URL` | Atlas connection string from step 1 |
   | `MAIL_USERNAME` | `khadamni303@gmail.com` |
   | `MAIL_PASSWORD` | Gmail **app password** (16 chars, not the account password) |
   | `MAIL_FROM` | `khadamni303@gmail.com` |
   | `GROQ_API_KEY` | from <https://console.groq.com> |
   | `SUPABASE_URL` | Project URL from step 2 |
   | `SUPABASE_SERVICE_KEY` | `service_role` key from step 2 |

   `SECRET_KEY` is generated by Render; the rest have defaults in `render.yaml`.

5. **Create Web Service**. The first build takes ~5 minutes (npm install plus
   pip install).

Health check: `https://<your-app>.onrender.com/api/health` → `{"status":"ok"}`

### Free plan caveat

The service sleeps after 15 minutes of inactivity, and the next request takes
~50 seconds to wake it. For a live demo, open the site a minute beforehand. The
Starter plan (~$7/mo) removes the sleep.

## Running locally

Nothing above changes local development — the Vite dev server still proxies to
`localhost:8000`, and with `SUPABASE_URL` blank, uploads stay in
`backend/uploads/`.

```bash
# terminal 1
cd backend
venv\Scripts\activate
uvicorn app.main:app --reload

# terminal 2
cd frontend
npm run dev            # http://localhost:5173
```

Copy `backend/.env.example` to `backend/.env` and fill it in first.

### Testing the production build locally

```bash
cd frontend && npm run build
cd ../backend && STATIC_DIR=../frontend/dist uvicorn app.main:app
# everything on http://localhost:8000
```

## What changed for deployment

| Problem | Fix |
|---|---|
| WebSocket hardcoded `:8000`, breaks on HTTPS | uses `window.location.host`; Vite proxies `ws` in dev |
| Uploads on local disk, wiped on redeploy | `app/services/storage.py` → Supabase, local fallback |
| `/uploads/<file>` served by `StaticFiles` | route redirecting to the Supabase public URL |
| CORS pinned to `localhost:5173` | same origin in production; `CORS_ORIGINS` for extras |
| No container | multi-stage `Dockerfile`, frontend build → `backend/static` |

The database still stores bare filenames and the frontend still requests
`/uploads/<filename>`, so no migration is needed — existing records keep working
once their files are uploaded to the bucket.
