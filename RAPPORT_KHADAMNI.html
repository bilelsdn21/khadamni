📋 Project Overview

Khadamni is a full-stack Tunisian home-services marketplace. Three roles interact with the platform — Clients, Providers, and a Moderator. The complete job cycle runs in one app: discovery on a live map, AI-powered request analysis, WebSocket negotiation chat, real-time GPS tracking during the job, post-job ratings, and a moderation dashboard with AI dispute mediation.

React SPA

Single-page application served as static assets. Communicates with the backend via HTTPS REST for all data operations and via a persistent WSS WebSocket connection for real-time events. Fetches static images from the backend's /uploads mount.

FastAPI Backend

Core application server. Exposes ~50 REST endpoints across 9 routers plus one WebSocket endpoint. Sole integration point with all external services — keeps API keys server-side and prevents credential exposure to the browser.

WebSocket Manager

In-process component within FastAPI. Maintains a registry of active WebSocket connections keyed by request_id. Broadcasts chat messages, typing indicators, GPS position updates, price offer events, and job completion notifications.

MongoDB (10 collections)

Persistent document store. 2dsphere geospatial index on provider_profiles.location enables efficient radius queries for map discovery. ObjectId references link documents across collections.

🔐 Authentication — JWT + OTP + Trusted Devices

Three-layer authentication: bcrypt password verification, 6-digit OTP email code, and persistent trusted device tokens to skip OTP on known devices.

Login Flow

1
POST /api/auth/login — verify email + bcrypt password. If the device token in localStorage matches a stored token, skip OTP and return JWT immediately.
2
Otherwise: generate 6-digit OTP → store in otp_codes collection with 5-minute expiry → send via Gmail SMTP.
3
POST /api/auth/verify-otp — check code, delete it (one-time use), return JWT access token + user data + new UUID device token (stored for 30 days).
4
Frontend stores JWT in localStorage. Axios interceptor attaches Authorization: Bearer <token> to every request automatically.

Suspension System

Suspended users can log in but see a full-screen overlay with the suspension reason and a live countdown timer. If the suspension has expired by the time they log in, it is auto-lifted in the database before returning the user object. Permanent suspensions show no timer.

# auth_service.py — auto-lift expired suspensions on login
if user.get("suspended"):
    until = user.get("suspended_until")
    if until and datetime.now(timezone.utc) >= until:
        await db.users.update_one(
            {"_id": user["_id"]},
            {"$set": {"suspended": False, "suspended_until": None, ...}}
        )

Token Architecture

JWT Access Token

HS256 signed. Carries sub: user_id. Default 30-minute expiry (extended to 30 days with "remember me"). All protected routes call get_current_user() which decodes this token.

Trusted Device Token

UUID stored in device_tokens collection and in the browser's localStorage. Valid 30 days. Allows skipping the OTP step on the same device. Can be revoked via POST /api/auth/remove-devices.

📍 Providers & Geospatial Search

Providers are stored with a GeoJSON Point in their profile. MongoDB's 2dsphere index enables distance-sorted proximity queries. Geocoding is proxied server-side to avoid CORS issues with Nominatim.

Provider Profile Storage

When a user registers as provider, a provider_profiles document is auto-created with their location stored as both flat latitude/longitude fields AND a GeoJSON Point {"type": "Point", "coordinates": [lng, lat]}. The GeoJSON field is what MongoDB uses for geospatial queries.

Map Discovery

The map page loads all available providers via GET /api/providers/all_providers. Each provider appears as a Leaflet marker. Clicking a marker shows a popup with name, rating, categories, and a "View Profile" button. The AI panel can filter providers by category match.

📡 Live GPS Tracking

During an active job, the provider's position is streamed over the existing WebSocket channel. The client sees the provider move on a live map with an OSRM-computed driving route between them.

Provider Side

navigator.geolocation.watchPosition with enableHighAccuracy: true fires when GPS updates. Position is sent over WebSocket (type: gps) at most once every 3 seconds. Profile coordinates are used as fallback if GPS is unavailable.

Client Side

Receives gps WebSocket events and moves the provider marker on the Leaflet map in real time. OSRM computes the driving route on demand: router.project-osrm.org/route/v1/driving/{lng,lat};{lng,lat}?overview=full&geometries=geojson

OSRM Route Factors

OSRM uses the OpenStreetMap road network and finds the fastest route considering: road type (highway vs local), turn restrictions, one-way streets, speed limits, and road connectivity. It does not account for real-time traffic — it is a static graph algorithm (Contraction Hierarchies for very fast computation).

🤖 AI Features — Groq / Llama 3.3-70B

Two AI flows use the same Groq inference client. Both return structured JSON — the model is instructed to use response_format: json_object to guarantee parseable output.

1. Request Analysis

Client writes their request in Tunisian dialect (a mix of Arabic, French, and local slang). The AI interprets it and returns: service category, urgency level, price estimate (min/max in Tunisian Dinars), a professional French description, and key points. This is stored and shown to the provider.

2. Dispute Mediation

When a client or provider files a report, the AI reads the full chat history (with roles labeled) and produces: a timeline summary, a recommendation (client_favored / provider_favored / neutral / insufficient_evidence), a confidence score, and a suggested action. The report is stored and surfaced in the moderator dashboard.

AI Panel — Map Page

On the map, clients can describe what they need in natural language. The AI returns a list of matching provider suggestions for both in-place and remote jobs. If the client navigates to a provider's profile and returns, the AI results are preserved via sessionStorage — no need to re-query.

🛡 Moderator System

The moderator role is completely isolated from the client/provider experience. Every moderator endpoint requires role === "moderator" at the backend. Frontend routes are guarded by NonModeratorRoute and ModeratorRoute wrappers.

Account Isolation

Moderators are redirected to /moderator on login. URLs like /map, /requests, /chat/*, /tracking/* redirect them back to the dashboard. The floating chat button is hidden. The sidebar only shows "My Profile" and "Moderator Panel".

User Management

The moderator can search/filter all users, suspend with a reason and duration (1d / 3d / 1w / 1m / permanent), activate, edit fields, or delete with full cascade cleanup. Suspension sends an automatic email to the user.

Report Review

Each report card shows: who reported whom (name + role), the actual report reason text, and the AI analysis (expandable). The moderator can suspend or delete the reported user directly from the report card without leaving the reports section.

Platform Statistics

Dashboard header shows: total users, request counts by status, open reports, active suspensions, and top 3 service categories for both in-place and remote jobs (computed via MongoDB aggregation pipeline).

Suspended User Experience

A suspended user can still log in. Instead of being blocked at the API, they see a full-screen overlay showing the suspension reason, a live countdown timer (updates every second), and the exact date their suspension expires. Permanent suspensions show "Permanently suspended" with no timer. A "Sign out" button is the only action available.

⭐ Ratings & Portfolio

Ratings System

After a job is marked complete, both the client and the provider can rate each other (1–5 stars + optional comment). Ratings are one-per-party-per-job. The provider's rating_avg and rating_count in provider_profiles are updated atomically on each new rating. Ratings appear on the public profile page.

Provider Portfolio

Providers can upload photos of past work with descriptions. Images are stored in the backend's /uploads/ directory and served as static files. Clients browsing a provider's public profile can scroll through the portfolio grid before sending a request.

🔒 Security Design

Role-Based Access Control

Every sensitive backend endpoint checks current_user["role"]. Moderator endpoints use a require_moderator() dependency that raises 403 if the role is not "moderator". Client-only actions (create request, cancel) raise 403 for providers and moderators. Provider-only actions (accept, reject, complete) raise 403 for others.

Frontend Route Guards

NonModeratorRoute redirects moderators away from client/provider pages at the React Router level. ModeratorRoute redirects non-moderators away from the dashboard. No client-side trick can bypass the backend role checks — the frontend guards are UX only.

JWT Security

HS256-signed tokens stored in localStorage. The get_current_user() FastAPI dependency decodes and validates the token on every protected request. Expired or tampered tokens raise 401. No server-side session storage is needed — the JWT is fully self-contained.

Input Validation

Pydantic models validate all request bodies at the FastAPI layer before any service logic runs. Passwords are hashed with bcrypt (cost factor 12). Disposable/temporary email addresses are blocked at registration using an offline domain list. File uploads are validated for size (5 MB max) and MIME type.

Chat/Tracking Isolation

The WebSocket endpoint validates the JWT token from the query string on connect. The HTTP chat endpoint verifies the user is a party to the specific request before allowing access. Moderators get explicit 403 on all chat, request detail, and tracking endpoints.

Suspension Enforcement

Suspended users can log in (to see why), but see a full-screen overlay blocking all interaction. Suspension is checked and auto-lifted at login time if the period has expired. The moderator can lift it manually at any time. Suspension emails are sent automatically with reason and expiry date.

⚖️ Technical Decisions

Why MongoDB instead of a relational database?

The schema varies significantly by role — clients have no provider_profile, providers have different fields than clients, and moderators are a completely different entity. MongoDB's document model eliminates NULL columns. The 2dsphere geospatial index for radius queries is also a first-class feature. The tradeoff is that cross-collection joins (lookups) require explicit aggregation pipelines instead of SQL JOINs.

Why WebSocket instead of polling?

A single persistent WebSocket connection handles chat messages, typing indicators, price offers, GPS position updates, and job status events simultaneously. With polling, each of these would require a separate interval hitting the server — much higher latency and server load. The tradeoff is connection state management (reconnection logic, connection cleanup on disconnect).

Why is geocoding proxied through the backend instead of called directly from the browser?

Nominatim's terms of service require a meaningful User-Agent header and discourage high-volume browser calls. Routing all geocoding through the backend allows rate limiting and caching to be applied centrally, and avoids CORS configuration on the client side.

Why Groq + Llama 3.3-70B instead of OpenAI?

Groq's inference hardware (LPUs) provides the fastest available inference for large models. Llama 3.3-70B is open-source, multilingual, and handles Tunisian dialect well. The free tier is sufficient for a thesis demonstration. OpenAI's API would be more expensive for the same quality.

Why allow suspended users to log in instead of blocking them at the API?

Blocking login returns a generic 403 with no context. Allowing login and showing a clear overlay with the reason, expiry date, and countdown timer gives users transparent feedback and a better experience. They can read why they were suspended and when their access returns, without needing to contact support just to find out their status.

Why trusted device tokens instead of just long-lived JWTs?

Long-lived JWTs cannot be individually revoked (the secret key revokes all tokens). Device tokens are stored in MongoDB and can be deleted per-device or all-at-once via POST /api/auth/remove-devices. This gives users control without forcing them to re-authenticate on every login.

❓ Jury Q&A

Anticipated questions from the thesis jury with precise answers.

What is the difference between a provider_profiles document and a users document?

The users collection stores authentication data (email, password hash, role, suspension status). The provider_profiles collection stores service-specific data (categories, location GeoJSON, rating_avg, hourly_rate, portfolio). This separation allows the map query to run entirely against provider_profiles with the geospatial index, without loading user auth data.

How do you prevent a client from impersonating a provider in the WebSocket?

The JWT token is validated on WebSocket connect via get_user_from_token(). For GPS messages (type: gps), the server checks that the sender's user ID matches the provider_id of the service request before accepting the position update. A client sending a gps event would be ignored.

What happens if the WebSocket connection drops during a job?

The frontend detects ws.onclose and shows a "disconnected" indicator. All message history is persisted in MongoDB, so on reconnect the client fetches history via the HTTP endpoint and re-establishes the WebSocket. No messages are lost.

How does the AI know what service category the request belongs to?

The Llama 3.3-70B model is given the list of available categories in the prompt and instructed to return exactly one from the list. The response format is set to json_object to guarantee parseable output. A Python JSON parser reads the result — if parsing fails, the endpoint returns 500.

How do you ensure the moderator cannot access client/provider data?

Two layers of enforcement: (1) Frontend — NonModeratorRoute redirects moderators to /moderator if they navigate to restricted URLs. (2) Backend — GET /api/requests/my, GET /api/requests/:id, all chat endpoints, and the AI report submission endpoint explicitly check role !== "moderator" and return 403. The moderator's JWT carries their role, and the backend reads it on every request.

How is the OSRM route computed?

The frontend calls the public OSRM demo server: router.project-osrm.org/route/v1/driving/{lng,lat};{lng,lat}?overview=full&geometries=geojson. The response includes a GeoJSON LineString of the route, which react-leaflet renders as a polyline on the tracking map. OSRM uses the OpenStreetMap road network and Contraction Hierarchies for fast shortest-path computation.

How do you handle the case where the provider's GPS is inaccurate?

navigator.geolocation.watchPosition is called with enableHighAccuracy: true to use hardware GPS instead of IP-based geolocation. If geolocation fails entirely, the provider's registered profile coordinates are used as a static fallback position. This prevents showing the provider in a wrong location (e.g., Algeria via IP geolocation).

What is the database structure for a dispute report?

The reports collection stores: request_id, reporter_id, reporter_role, the user's reason text, and ai_analysis (an embedded object with summary, recommendation, confidence, suggested_action, timeline). When the moderator fetches reports, the endpoint enriches each document with reporter and reported user names/emails by doing two additional MongoDB lookups per report.
